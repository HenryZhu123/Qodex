# 知识库评估说明（审校场景）

本文只针对**题目审校**这一使用场景，回答四个问题：

1. 评估知识库在审校中的作用，需要准备什么？
2. 测试集要多少才够用？
3. 主要看哪些指标？
4. 指标达到多少算合格、多少算优秀？

> 范围说明：本项目的知识库只服务于**审校**。生成与组卷不在本模块范围内，因此不评估"按知识点出题""知识点覆盖度"等指标，也不要求知识点映射。

---

## 1. 评估需要准备什么

### 1.1 软件环境

| 项 | 要求 |
|---|---|
| Python | 3.10+ |
| 知识库依赖 | `pip install -r requirements.txt`（PyMuPDF、python-docx 或 docx2txt、charset-normalizer、BeautifulSoup、lxml、jieba） |
| 扫描件 OCR | MinerU Agent API（免 token，按 IP 限流）或 Tesseract + `chi_sim` |
| 数据库 | 无需外部服务，SQLite 随 Python 自带 |
| 审校侧 | pi agent + 审校技能；模型走 Talkweb 中转站 |

### 1.2 语料（学科证据）

知识库的语料是教材：

| 学科 | 教材 |
|---|---|
| 数据结构 | 严蔚敏《数据结构（C 语言版）》第 2 版 |
| 计算机组成 | 谭志虎《计算机组成原理》 |
| 操作系统 | 汤小丹《计算机操作系统（慕课版）》 |
| 计算机网络 | Kurose & Ross《Computer Networking: A Top-Down Approach》 |

这 4 本是 408 四门课的权威教材，覆盖审校所需的学科事实。

### 1.3 参考题库

已建成 720 道 408 历年选择题（2009–2026，18 年 × 40 题），标准答案 100% 覆盖。

用途有两个：

1. **正样本**：干净、答案正确的题目，用于确认审校**不误报**；
2. **同题答案比对**：给定题面 + 卷面答案，判断是否与标准答案一致。

### 1.4 错题集（负样本）

用 `question-error-synthesis` 技能从参考题生成：每道干净题注入**一种**指定错误，得到"错题 + 标准答案 + 错误位置 + 最小修正"。

这是审校测试的核心输入——没有它，无法测 Recall。

### 1.5 审校查询集（检索评估用）

每条记录：

```json
{
  "query_id": "rq001",
  "question_id": "refq-408-2019-30",
  "claim": "死锁的四个必要条件是互斥、请求保持、不可剥夺、循环等待",
  "suspect_type": "factual_logical",
  "expected_verdict": "supports",
  "gold_chunk_ids": ["<doc_id>:00167"],
  "gold_heading": "3.7 死锁概述",
  "gold_pages": [121]
}
```

`expected_verdict` 取 Proposal §3.6 的三态：

- `supports`：证据支持“这个陈述成立”
- `refutes`：证据显示陈述不成立
- `unclear`：检索不到相关证据

### 1.6 环境隔离

- 每次评估使用独立 run 目录；
- 记录 commit、依赖版本、seed；
- 评估语料不得同时用作调参集。

## 2. 测试集要多少才够用

### 2.1 按目标推荐规模

| 目标 | 参考题（正样本） | 合成错题（负样本） | 检索查询 |
|---|---:|---:|---:|
| 冒烟测试（能跑通） | 20 | 20 | 20 |
| 功能覆盖（九类错误都跑到） | 100 | 180（每类 20） | 100 |
| 可信评估（可写进报告） | 300 | 450（每类 50） | 200 |
| 学术级评估 | 600+ | 900+（每类 100） | 400 |

当前已有 720 道参考题，**满足可信评估与学术级评估的正样本需求**。

### 2.2 负样本的错误类型配额

Proposal §4.2 的九类错误，每类至少：

| 错误类型 | 最小 | 推荐 |
|---|---:|---:|
| 错别字 | 20 | 50 |
| 标点符号错误 | 20 | 50 |
| 选项结构错误 | 20 | 50 |
| 信息缺失 | 20 | 50 |
| 题目与题型不一致 | 20 | 50 |
| 答案泄露 | 20 | 50 |
| 语义不清 | 20 | 50 |
| 题目无解 | 20 | 50 |
| 事实/逻辑错误 | 20 | 50 |

### 2.3 规模下限判断

- **正样本**：至少 100 道，否则误报率（FPR）的置信区间过宽；
- **负样本**：每类至少 20 道，否则该类 Recall 无法稳定估计；
- **检索查询**：至少 100 条，否则 Recall@5 波动大；
- **对照**：必须同时有"有知识库"和"无知识库"两组，各跑同一批样本。

> 结论：**可写进报告的规模是 300 正样本 + 450 负样本 + 200 查询；最低可用规模是 100 正样本 + 180 负样本 + 100 查询。**

## 3. 评估指标

分三层：知识库自身的检索质量、审校对知识库的使用质量、端到端审校质量。

### 3.1 知识库检索层

对应 Proposal §4.4 的四个指标：

| 指标 | 定义 | 怎么算 |
|---|---|---|
| **P@1** | 第一条结果就是相关证据的查询比例 | 人工或 gold chunk 判定 |
| **Recall@5** | 前 5 条中至少命中 1 个 gold chunk 的查询比例 | gold chunk 比对 |
| **evidence groundedness** | 返回的证据是否真的支持/反驳该陈述的比例 | 人工判定 200 条 |
| **retrieval time** | 单次检索耗时 | 程序计时 |

辅助指标：

| 指标 | 定义 |
|---|---|
| 锚点完整率 | 带 `heading_path` + `page` 的证据比例 |
| 无证据率 | 搜索无结果的比例（应只在确实无相关材料时发生） |

### 3.2 审校端到端

对应 Proposal §4.2：

| 指标 | 定义 |
|---|---|
| Precision | 报出的问题中真问题的比例 |
| Recall | 真问题中被报出的比例 |
| F2 | 偏向 Recall 的调和平均（漏报代价高于误报） |
| FRR | 假接受率（有错却判为通过） |
| 处理耗时 | 单题审校时间 |

### 3.3 知识库的增益（核心实验）

| 指标 | 定义 |
|---|---|
| ΔPrecision | 有知识库 Precision − 无知识库 Precision |
| ΔRecall | 有知识库 Recall − 无知识库 Recall |
| ΔFPR | 有知识库 FPR − 无知识库 FPR |
| 触发率 | 实际调用知识库的题目比例（Router 是否过度检索） |

## 4. 数值门槛

假设测试集达到"可写进报告"规模（300 正样本 + 450 负样本 + 200 查询）。

### 4.1 知识库检索层

| 指标 | 合格 | 优秀 |
|---|---:|---:|
| P@1 | ≥ 0.60 | ≥ 0.80 |
| Recall@5 | ≥ 0.75 | ≥ 0.90 |
| evidence groundedness | ≥ 0.70 | ≥ 0.85 |
| retrieval time（单次） | ≤ 300 ms | ≤ 100 ms |
| 锚点完整率 | 100% | 100% |

### 4.2 审校端到端

Proposal §4.2 给出的门槛：

| 指标 | 合格 | 说明 |
|---|---:|---|
| 每类 Precision | ≥ 90% | 硬性要求 |
| 每类 Recall | ≥ 90% | 硬性要求 |
| FRR | < 10% | 硬性要求 |
| 无未处理的失败样本 | 必须 | 超时/失败要显式报告 |

当前系统的实际水平（p0 检测评测结论）：

| 指标 | 实测值 |
|---|---:|
| F1 | 0.877 |
| Recall | 82.4% |
| Precision | 93.8% |
| **FPR** | **27.9%** |

**这说明单纯靠 LLM 判断达不到 90%/90% 门槛，FPR 尤其偏高。** 这正是知识库要解决的问题：用外部证据把 FPR 压下来。

### 4.3 知识库的增益

| 指标 | 合格 | 优秀 |
|---|---:|---:|
| ΔPrecision | ≥ +3 个百分点 | ≥ +8 个百分点 |
| ΔFPR（下降） | ≥ −5 个百分点 | ≥ −10 个百分点 |
| 触发率 | 30%–70% | 40%–60% |

> 触发率过高说明 Router 过度检索，成本浪费；过低说明知识库没被真正用上。

## 5. 评估流程

1. **准备数据**：4 本教材入库 → 720 道参考题入库 → 合成错题 → 构建查询集。
2. **冻结版本**：记录 commit、教材版本、seed。
3. **跑知识库指标**：用查询集测 P@1、Recall@5、groundedness、耗时。
4. **跑审校（有知识库）**：对正样本和负样本各跑一遍，统计 P/R/F2/FRR。
5. **跑审校（无知识库）**：同一批样本，关闭检索，再统计。
6. **计算增益**：ΔPrecision、ΔRecall、ΔFPR。
7. **分析失败**：逐条看知识库没帮上忙的案例，判断是检索问题还是证据问题。

---

## 6. 必须做的消融

| 消融项 | 做法 | 观察指标 |
|---|---|---|
| 关闭知识库 | 审校不调用检索 | ΔPrecision、ΔFPR |
| 只保留字面检索 | 关掉向量通道 | Recall@5 下降幅度 |
| 关闭锚点校验 | 不做分块归属检查 | groundedness |
| 关闭 Router | 每题都检索 | 触发率、总耗时 |
| 换分块策略 | `--mode paragraph` 强制 | Recall@5 |

## 8. 常见坑

1. **只测负样本**：不测干净题就看不出误报，而误报是本项目的主要痛点。
2. **查询集从原文直接抄**：把教材原句当查询会虚高 Recall，应改写成审校里真实出现的陈述。
3. **不做有/无对照**：只报"有知识库"的数字，无法证明知识库有用。
4. **正负样本同源**：用同一道题的原题和它的错题分到不同集合，会造成泄漏。
5. **忽略无证据场景**：`unclear` 必须被正确返回，否则系统会把"没查到"当"没问题"。
6. **只看平均值**：要同时报最差错误类型的表现，避免被平均掩盖。
